## Context

微信公众号编辑器没有真正的 `<h2>`。作者写「章节小标题」时，是靠**视觉**表达的：
把一行文字放大、居中、（有时）加粗。工具从 URL 抓到的是这堆内联样式，必须**反推**
哪一行是小标题、哪一行是图注、哪一行是正文。`api/wechat_blocks.go` 的 `emit()`
就是这个反推分类器。

这个分类器过去 3 个月被反复修，仍反复漏判标题。相关提交（同一族）：

| 提交 | 干了什么 |
|---|---|
| `98b786c` recognize WeChat URL headings with inner span styles | 处理外层 `<b>` 被内层 span `font-weight:normal` 覆盖 |
| `72b17f6` 居中大字号小标题被误判为图注 | 加「大字号」否决图注 |
| `b5ede04` tighten WeChat heading classification | **同时引入** `allRunsUnderBoldTag`（要 `<b>`）+ `isCenteredTitleLikeHeading`（**要冒号**） |
| `389a177` 章节标题不再误判为图注 | 继续在图注侧调字数/信号 |
| `a320e39` 显式 Word 标题样式在场时停用启发式 | DOCX 侧（另一个领域） |

两份 WORKLOG（`docs/worklogs/WORKLOG-heading-vs-caption-2026-07-01.md`、
`docs/worklogs/WORKLOG-docx-heading-signal-priority.md`）都记录了「修了很多次修不好」。

## Goals / Non-Goals

**Goals:**
- 让形态一致的章节小标题被一致识别，不论作者有没有多打一个 `<b>`、有没有冒号。
- 用**移除**巧合依赖（而非新增排除条件）来根治——符合「优雅 = 用最少的新概念达成目的」。
- 沉淀一条**过程护栏**，让同族问题不再靠「下一篇撞上就再加一条正则」维持。

**Non-Goals:**
- 不追求 100% 无误判——不存在能读心作者意图的规则。目标是判据落在**第一性信号**上，
  剩余误差是可解释、可接受的（居中大字的导语/金句偶尔被当标题，属良性）。
- 不动 DOCX 侧 `heading-detect.js`（不同输入生态，另一个领域）。
- 不动 FoodTalks 网站渲染器（红线 #19 物理隔离）。

## Decisions

### 决策 1：小标题判据收敛到「字号相对正文放大 + 居中」，删掉加粗/冒号必要条件

**为什么反复出错（第一性归因）——这就是报告要回答的问题：**

微信里区分「小标题 vs 正文 vs 图注」的**唯一稳定维度是字号相对正文的方向**：
正文恒 15–17px、图注 ≤14px、只有小标题上探到 18px+（这一点 WORKLOG-2026-07-01 自己
就写明了）。「居中」对图注和标题都成立，是弱信号但方向对。而「有没有 `<b>`」「有没有冒号」
**根本不是标题的定义属性**——它们只是某几篇样例文章里标题恰好长的样子。

历次修复的错误动作是：每漏判一篇，就去看那篇标题**碰巧**都有什么（第一篇碰巧都在 `<b>` 里，
第二篇碰巧都带冒号「文化美好：…」），把这个巧合属性加成**必要条件**。于是识别框被
`allBold` → `allRunsUnderBoldTag`（要 `<b>`）→ `isCenteredTitleLikeHeading`（要冒号）
三个 OR 分支越描越窄，每个分支只认它那一篇的形状。当一篇标题**三个巧合一个都不占**
（居中 + 20px + 无 `<b>` + 无冒号，正是 02「四大品牌差异化竞争策略拆解」），它就从所有分支的
缝里漏下去，掉成正文。

真值对照（同一篇文章、逐字节抓取的两个标题）：

| | 01 新鲜零食四强品牌共性特征 | 02 四大品牌差异化竞争策略拆解 |
|---|---|---|
| 对齐 | center | center |
| 字号（内层 span） | 20px | 20px |
| 颜色 | rgba(0,0,0,.9) | rgba(0,0,0,.9) |
| 外层 `<b>` | **有** | **无**（作者漏加粗） |
| 冒号 | 无 | 无 |
| 旧判据结果 | `allRunsUnderBoldTag` 命中 → h | 三分支全落空 → **txt（漏判）** |

**方案：** 把 `isCenteredTitleLikeHeading` 的冒号闸门删掉，重命名为 `isCenteredLargeHeading`：
`居中 + 字号≥18（外层已保证）+ ≤40字 + 非图片来源行/参考头/灰色或小字图注` ⇒ 标题。
加粗（`allBold`/`allRunsUnderBoldTag`）保留为**充分不必要**的额外命中路径。

**为什么选「删条件」而不是「加一条分支专收 02」：** 加分支是第五个创可贴，下一篇没冒号也没
数字编号图的标题照样漏。删掉巧合依赖、回到第一性信号，才是把病根拔掉。这正是全局记忆
`feedback_no_bandaid_fix_audit_whole_path`（禁止创可贴、系统化修复）的要求。

**Alternatives considered:**
- *结构信号：「编号图（01/02）后的第一行 = 标题」*。对本文有效，但「什么算编号图」本身又是
  一条 pattern 特定规则（按 data-ratio？alt？），是**新增概念**，换个不用编号图的排版又失效。否决。
- *再加一条排除正则维持现状*。就是过去 4 次的做法，被本次根因否定。否决。

### 决策 2：过拟合的负向测试必须删除，负向样例只能来自真实文章

旧测试 `TestCenteredLargeWithoutBoldTagIsNotHeadingNorCaption` 用编造的
「居中放大但没有加粗标签的一行」断言「这不该是标题」。**没有任何真实文章长这样**——
它是开发者臆想出来「万一有呢」的边界，为了给冒号闸门背书。结果这条臆想边界恰好切穿了
02 这样的真标题，而且它**测试通过**给了「分类器是对的」的假信心（违反规则 #9：测试应验证
「为什么重要」，而不是把创可贴的行为固化下来）。

改写为：以真实病样 02 标题的 HTML 形态断言「它就该是标题」。负向守护改为只保留有真实
文章支撑的那些（图片来源行、参考来源头、灰/小字图注、左对齐大字 callout——这些都有真样例）。

### 决策 3（防再犯护栏）：分类器 bug 的修复协议

写进 spec，成为此后所有标题/图注判据改动的强制流程：

1. **最小差分定位**：拿被误判项的**真实 HTML**，和一个被**正确**分类的同类兄弟逐字节对比，
   找出唯一的真实差异（本次 = 少一个 `<b>`）。
2. **追问语义**：这个差异**承载标题语义**吗？还是只是这批样例的巧合？（`<b>`/冒号 = 巧合。）
3. **若现规则依赖巧合 ⇒ 删依赖，不加分支**。回到第一性信号。
4. **全样例回归**：改完必须一次性跑通**全部历史病样**（不是只跑新的那篇），负向用例只能引真实文章。

## Risks / Trade-offs

- **[居中大字的非标题被判成标题]**（如居中金句、居中导语）→ Mitigation：① 字号必须严格
  ≥18px（>正文 17px），把绝大多数正文/导语挡在门外；② 图片来源/参考头/灰或小字图注仍显式否决；
  ③ 即便偶有居中大字金句被当标题，视觉是「加粗大字独占一行」，与作者本意（强调）一致，属良性误差，
  远好于把真章节标题降级成正文。回归已确认既有负向守护（左对齐大字、灰/小字图注、来源行、参考头）
  **全部不变**。
- **[有人日后又想加回冒号/加粗必要条件]** → Mitigation：spec 的 REMOVED 段 + 决策 3 协议明确
  禁止；`TestCenteredLargeTitleWithoutBoldNorColonIsHeading` 会在任何人加回闸门时立刻变红。
- **[≤40 字上限偏严]**：实测标题最长 25 字、02 为 13 字，40 留足冗余；超长「加粗强调正文」由
  外层 ≤80 字 + 非居中双重拦截，不受影响。

## 对抗性复核（Codex）与结论

修复后交 Codex 独立对抗测试（8m52s，只加失败测试、不碰生产代码）。逐条实跑复核后的裁定：

| Codex 发现 | 裁定 | 处理 |
|---|---|---|
| 13.5pt 块级字号被算成 17.9955px 漏判标题 | **真 bug** | ✅ 采纳：`pt` 换算 `*1.333` → `*96/72`（96dpi 精确，13.5pt=18px）。守护 `TestPtFontSizeHeadingPrecision` |
| 居中大字「金句/导语/整句强调」被误升为标题 | **真·部分可修** | ✅ 采纳：加「句号/逗号收尾否决」（与 DOCX 侧 `isBoldHeading` 一致；放行 ？！ 疑问/感叹标题）。守护 `TestCenteredLargeSentenceEndingIsNotHeadingButLabelIs` |
| 17.5px / 1.1em / 纯文字「01」标题漏判 | **Codex 臆想** | ❌ 不采纳：17.5px/1.1em 是它编的卡阈值数值；真实微信标题恒 18–20px+，「01/02」在真文章里是**图片**不是文字。正是本次要防的「拿构造边界当真值」 |
| 41–80 字非加粗居中长标题漏判 | **按设计** | ❌ 不采纳：真标题都很短；41–80 字居中非加粗块更可能是导语。内层 ≤40 严于外层 ≤80 是**有意的保护**（别把长导语误升成标题） |
| rgba alpha 被忽略 / `isGreyHex[100,200]` 边界（如 #636363、rgba(0,0,0,.35)） | **真·瑕疵但极罕见** | ➖ 记为已知局限：微信图注恒用 #888 实心灰，半透明灰/擦边灰在真文章几乎不出现。为假设情况加复杂度=过度设计，不动 |

**结论**：Codex 未推翻核心修复（方向正确）。净收获 = 2 个第一性、与 DOCX 侧一致、零/低风险的加固。
残留的「居中大字无句末标点的 callout」（如「新品上市 低糖高蛋白燕麦拿铁」）仍会被判标题——这是
「标题和 callout 视觉本就一样、无文字信号可分」的固有代价，属良性（渲染为加粗独占一行，接近作者本意），
且远好于把真章节标题降级成正文。若日后要更精准，唯一出路是引入「标题需紧跟编号图/图片」的**结构信号**
（见 Open Questions，本次未做，避免新增概念）。
