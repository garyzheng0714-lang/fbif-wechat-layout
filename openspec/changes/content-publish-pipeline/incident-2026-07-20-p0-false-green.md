# 2026-07-20 FBIF 公众号自动排版 P0 事故报告

## 1. 结论

这是一次 **P0 级“漏处理 + 假正常”事故**，不是单纯的“排版慢”。

2026-07-20 10:37，`FBIF食品饮料创新` 同一批发布 4 篇文章。另一个飞书信息源在 10:38 已经发出文章通知，但资讯订阅系统依赖的供应商直到 11:01:39—11:06:58 才把 4 篇文章分批送到我方。第一篇进入数据库后，外部看门狗在 11:02:48 就宣布“已恢复”；当时另外 3 篇尚未全部入库，第一篇也尚未完成排版和审核卡发送。11:04:48，看门狗又发出“每日心跳正常”。这两条绿色通知都不成立。

4 篇文章最终没有永久丢失：11:06:58 前全部进入资讯订阅数据库，11:11:38 前全部完成 FoodTalks 测试站草稿和飞书审核卡。但系统在业务闭环完成前错误恢复绿色，用户只能靠人工对照发现问题。这违反了 P0 红线。

事故的直接根因有三层：

1. **发现层单点依赖且供应商迟到**：另一个来源 10:38 已经知道新文章，我方供应商晚了约 23—29 分钟。
2. **监控定义错误**：健康检查只证明“今天至少收到 1 篇、服务进程还活着、任务没有超过宽松超时”，没有证明“这一批文章已经收齐、每篇已进入审核、每张审核卡已送达”。
3. **CI 验错了东西**：以前的 CI 测了单仓库函数和快乐路径，没有模拟“同一批 4 篇只先到 idx=2”“worker panic 后网页仍可访问”“第 5 次失败后任务被永久转人工”“事故恢复后马上又发心跳”等真实故障。

## 2. 影响

- 受影响公众号：`FBIF食品饮料创新`。
- 受影响文章：2026-07-20 10:37 发布的 4 篇普通文章。
- 用户可见影响：10:38 后没有按预期自动出现排版审核卡；系统随后错误发送“已恢复”和“每日心跳正常”。
- 数据影响：没有永久丢文；4 篇最终均进入审核。
- 信任影响：严重。监控把未完成说成正常，比直接报错更危险。

## 5. 错在哪里

### 5.1 发现层：单一供应商不是权威事件源

当前自动发现依赖供应商 webhook + 每 5 分钟查询同一供应商。二者看似两条路，实际上仍是同一个故障域。当天供应商的 webhook 晚到，主动 reconcile 也连续返回 0；因此补漏机制没有形成独立冗余。

飞书 Dudu 在 10:38 已有消息，证明公众号文章本身并非不可发现，而是我方选择的单一供应商链路更晚。系统没有接入这个第二信号，也没有官方群发回调，因此无法在 10:38 自主知道完整批次。

### 5.2 监控层：把基础设施存活错当业务完成

旧 `/health/sync` 的绿色条件主要是：

- 自动规则存在；
- poller 有心跳；
- reconcile 最近执行过；
- 今天文章数不为 0；
- 已入库文章都有同步项；
- 普通文章没有超过 45 分钟仍未到审核；
- 没有明确 `failed` 或 `reconciliation_required`。

这些条件无法回答最重要的问题：**公众号这一批到底有几篇，是否收齐，每一篇是否完成排版，每一张审核卡是否送达。**

因此 `idx=2` 第一篇到达后，`TodayArticles` 从 0 变为 1，`expected_publication_not_observed` 消失。虽然缺 idx=1、3、4，虽然任务还在排版，健康接口仍可返回绿色。

### 5.3 执行层：worker 可以死，网页仍然活

同步 worker 与网页 API 在同一进程，但由普通后台 goroutine 启动。公共 `safe.Go` 会捕获 panic，避免整个网页进程崩溃；副作用是 worker panic 后可以直接退出，而 HTTP 服务器继续正常响应。旧健康接口没有同步 worker 心跳，所以这类状态会“网页正常、业务永久停摆”。

### 5.4 补偿层：第 5 次失败后停止自动修复

旧投递策略只对临时错误自动重试 5 次。第 5 次后任务转成“等待人工重试”。即使网络、令牌或下游服务随后恢复，任务也不会自己继续。对一个使用永久 `source_key`、天然可幂等重放的接口而言，这个停止条件没有必要，反而制造了永久停摆点。

### 5.5 通知层：恢复后立即发心跳

旧看门狗发送“恢复”时没有把当天心跳标记为已完成。下一轮两分钟检查发现健康，就又发“每日心跳”。CI 测试甚至明确期待这个错误行为，说明测试把错误产品语义固化成了“正确”。

## 6. 为什么已经提了四五次，仍然反复修不好

这是工程方法错误，不是需求不清楚。用户要求一直很清楚：监控 FBIF 新文章，自动排版，异常必须通知，不能漏。

|---|---|---|
| `26ccc844` | 09:53 | 增加可靠同步中心 |

这些改动每次只堵住刚暴露的一个孔，没有先定义并自动证明最终业务不变量：

> 对同一发布批次，全部文章被发现；每篇只建一个持久同步项；普通文章全部到 `awaiting_review`；每篇审核卡均已成功送达；任何一步未完成时不得绿色；暂时失败必须永久自动补偿。

反复失败的具体原因：

1. **按症状修，不按闭环修**：缺启动校验就补启动校验，缺回填就补回填，缺探针就补探针；没有从“用户必须看到全部审核卡”倒推每层证据。
2. **两仓库分别自证**：资讯订阅测试“已提交任务”，排版工具测试“能建卡片”，但没有测试两边合起来的最终状态。
3. **没有多图文部分到达用例**：旧测试只造一篇 `idx=1`，完全没覆盖真实的 `idx=2` 先到、随后 1/4 到、最后 3 到。
4. **没有假正常用例**：测试验证 HTTP 和配置，未断言“任何未完成项都必须让绿色消失”。
5. **没有 worker 死亡用例**：`safe.Go` 被当作可靠性增强，却没测试“panic 被 recover 后任务循环是否继续”。
6. **没有重试耗尽用例**：第 5 次后停人工被当成正常策略，没有按 P0 目标检查“服务恢复后能否自动续跑”。
7. **把超时阈值当完整性证明**：45 分钟内没完成仍显示绿色，本质是允许 45 分钟假正常。
8. **给出了没有证据的保证**：此前的“不会再发生”没有对应批次完整性、worker 心跳、最终卡片状态和故障注入测试。这类保证无效。

## 7. 本次底层修复

### 7.1 绿色条件改为业务闭环条件

新的绿色必须同时满足：

1. 自动同步规则存在且开启；
2. poller 心跳新鲜；
3. 同步 worker 心跳新鲜；
4. 供应商 reconcile 在窗口内持续运行；
5. 当日已入库文章与持久同步项一一对应；
6. 同一微信 `biz + mid` 批次的 `idx` 从 1 到当前最大值连续，不得缺号；
7. 最后一篇到达后满 10 分钟，避免第一篇到达就宣布整批完成；
8. 所有普通文章均已进入审核态；
9. 排版工具没有仍在处理的任务；
10. 审核通知 outbox 为空，且不存在应有但缺失的审核卡；
11. 没有失败任务、对账积压、重复 source key 或内容冲突；
12. 微信官方数据探针正常。

任一条件不满足，外部看门狗都看见 `ready=false`，不能发恢复或心跳。

### 7.2 worker 具备自证和自愈能力

- 每轮工作写持久 worker 心跳；HTTP 进程活着但 worker 不工作时，90 秒后 P0 红色。
- 单次 worker panic 在迭代边界恢复并记录堆栈，下一轮继续；整个 worker 循环本身意外崩溃或返回时，进程内 supervisor 也会在 1 秒后重新拉起，不再出现“网页活着、worker 永久退出”。
- 投递接口使用永久 `source_key` 幂等；任何网络、限流、5xx、鉴权或配置错误均保留持久任务并持续退避重试，不再第 5 次转人工停摆。
- 失败不会被吃掉：未完成同步项始终让业务健康保持红色。

### 7.3 排版和审核卡不再被当作“后台细节”

- 只要有排版任务仍在 processing，排版监控立即非绿色。
- 只要审核通知仍 pending/sending，排版监控立即非绿色。
- `awaiting_review` 但无审核卡、通知错误、重复任务、近期失败、对账状态继续 fail closed。

### 7.4 通知语义修复

- “已恢复”和“每日心跳”只允许在整批、审核态、审核卡三项均完成时发送。
- “已恢复”本身计为当天绿色确认，下一轮不能紧跟一条心跳。
- 消息文字明确写“文章批次完整、普通文章全部进入审核、审核卡全部送达”，不再只说“探针正常”。

## 8. CI 与故障注入门禁

两个仓库每个 PR 和每次 main 推送都无路径过滤地运行完整测试。新增具名 P0 门禁：

| 故障注入 | CI 必须证明 |
|---|---|
| 只收到同批 idx=2 | 缺 idx=1，绝不能绿色 |
| 收到 idx=1、2、4 | 缺 idx=3，绝不能绿色 |
| idx=1..4 已齐但最后一篇刚到 | 批次仍在稳定窗口，绝不能绿色 |
| 4 篇中任一未到审核 | `current_day_review_incomplete`，绝不能绿色 |
| worker 单轮 panic | panic 可见，下一轮仍能运行 |
| 重试计数已经达到 5000 | 任务仍在自动补偿队列，不得永久转人工 |
| 排版任务仍 processing | 排版监控非绿色 |
| 审核通知仍 pending | 排版监控非绿色 |
| 事故刚恢复 | 发一次恢复；同日下一轮不得再发心跳 |

这些测试不是“覆盖率数字”，而是直接锁住本次真实事故的状态序列。

## 9. 能保证什么，不能再假保证什么

### 9.1 可以做到的硬保证

在文章已经进入资讯订阅数据库之后，只要资讯订阅服务器、排版服务器和必要网络仍能运行：

- 文章与同步项原子落库，不存在“文章有了但没建单”的静默窗口；
- worker 不会因一次 panic 或重试次数耗尽而永久停止；
- 下游恢复后任务会自动续跑；
- 在全部审核卡送达前系统不会恢复绿色；
- 任一步无法推进，P0 状态持续为红，并由独立看门狗通知。

最重要的保证是：**不再把未完成说成正常。** 外部系统故障可能让完成变慢，但不能再静默、不能再假绿、不能再停止补偿。

### 9.2 仅靠当前单一供应商无法做到的物理保证

“公众号一发布，即使供应商完全不知道，我方也绝不漏”无法由我方服务器单独证明。原因很简单：如果公众号没有向我方发事件，而唯一供应商也没有返回文章，我方收到的状态与“今天确实没发文章”完全相同。代码无法从两个相同的空输入中推断外部真实世界的差别。

当前又明确不启用公众号服务器回调，所以要把“只有我方服务器宕机才可能发现失败”做成字面事实，必须增加一个独立发现源，二选一：

1. 把 10:38 已经能收到文章的飞书 Dudu 群消息接成第二入站源；或
2. 重新授权接入不会影响现有运营能力的官方/独立事件源。

在第二发现源接入前，批次 `idx` 连续检查和 10 分钟稳定窗口能阻止本次这种“idx=2 先到就恢复”的假正常，但无法证明一个只发布 idx=1 的单篇消息没有被供应商整体漏掉。这个边界必须明确保留，不能再用“绝对不会”掩盖。

## 10. 验收标准

1. 复现 idx=2 → idx=1/4 → idx=3 的到达顺序，前两阶段始终 `ready=false`。
2. idx 全齐但仍有普通文章未到审核时，始终 `ready=false`。
3. 所有文章到审核但审核卡 outbox 未清空时，始终 `ready=false`。
4. 最后一张审核卡送达且批次稳定满 10 分钟后，才允许一次“已恢复”。
5. 恢复后同一天不得紧接“每日心跳”。
6. 分别人为让单次任务和整个 worker 循环 panic；网页可继续访问，单次任务下一轮继续，整个循环由 supervisor 自动拉起，监控不假绿。
7. 人为让排版接口连续失败超过 5 次，任务仍自动重试；接口恢复后无需人工即可进入审核。
8. 两仓库完整测试、race test、看门狗测试全部通过后才允许部署。
9. 部署后用生产 `/health/sync`、`/api/publish/monitoring` 和 4 篇实际任务状态交叉核对。
10. 第二独立发现源未接入前，事故报告和健康说明不得宣称“发现层绝对不漏”。

## 11. 责任结论

需求没有歧义。反复失败的责任在实现和验证方式：以前用局部探针代替最终结果、用宽松超时代替完整性、用单篇快乐路径代替真实批次、用口头保证代替故障注入证据。本次修复的核心不是再加一句保证，而是让错误状态在数据结构、健康接口、自动补偿、通知状态和 CI 中都无法被解释成绿色。
