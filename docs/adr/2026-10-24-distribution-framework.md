# 多平台分发框架（2026-10-24 用户裁定）

状态：目标框架，按文末顺序迁移中。2026-10-27 用户改定：贴图线归「公众号贴图发布」项目，排版工具不做贴图入口，Feed 不改（见细则 7、迁移顺序第 6 步）。哪一步还没迁完，现行行为就仍以 [CLAUDE.md](../../CLAUDE.md) 红线为准；每迁完一步，同一次提交改掉对应红线。

## 为什么重定

用户原话（2026-10-24）：「你连最基础的架构和框架都没跟我确定好」「你现在连基础的框架都是错的，你整个东西都是乱的」「扫码测试应该是最后一步」。确认框架后：「先让 Codex 把这个框架挑一遍毛病，把控好进度，再开始改」。

当天读代码核对出来的问题：

- 同一条平台规则写了好几份。头条号标题 2–30 字（英文字母、数字两个算一个字）在 `api/yunsuo_platform_profiles.go`、分发服务 `service/platforms/toutiao.mjs`、`public/js/distribute-page.js` 各写一遍；平台说明书两个仓库各生成一份，已经对不上。
- 排版工具按平台把正文写成网页代码再交给分发服务。百家号收到的也是头条的图注写法，要靠分发服务再改一遍；分发服务的 `service/html.mjs` 写死只认 `pgc-img-caption`。
- 账号存了三份，互相对不上：排版工具的 `YUNSUO_TARGET_ACCOUNTS_JSON`（账号编号必须是 36 位云梭 UUID）、多维表格「平台账号」、云梭后台。排版工具发稿不带 account，表里同一平台有两个「在用」号时，存草稿报 `account_required`。
- 云梭已不接新稿，但 `loadYunsuoConfig` 仍要求云梭密钥，卡片、改稿页、上线检查、部署检查都依赖它，删掉云梭配置整个分发功能就停。
- 贴图进不来：机器入口只收 `content_kind=article`，Feed 把贴图记成「图集/小绿书不自动投递」停住。
- 分发记录只在两台服务器的 JSON 里，配置在 env 和管理后台，都没进多维表格。

## 框架

| 系统 | 只管 | 不管 |
| --- | --- | --- |
| `FoodTalks_Feed`（B 机） | 找新文章，交链接 | 排版；贴图（照旧记「不自动投递」，2026-10-27） |
| 排版工具（A 机） | 内容：抓原文、拆正文块、第三方通用规则、审核卡、发 FoodTalks、写分发记录 | 任何第三方平台的写法和限制 |
| 分发服务（B 机） | 平台：每个平台一个文件，写清标题字数、封面要求、正文块怎么写成这个平台的格式、编辑器点哪、怎么读回核对、哪些按钮禁点 | 内容规则、审核 |
| 公众号贴图发布（A 机 `fbif-sticker`） | 贴图：投稿、审核、建公众号贴图草稿、进表、贴图群卡片、同步到抖音小红书（2026-10-27 起贴图线归它） | 文章 |
| 多维表格（中台） | 平台账号（含来源公众号、通知群）、分发记录（看板）、小配置 | 真相：发布状态以服务器 JSON 为准 |

文章线和贴图线是同一个样子：一个系统交内容（文章是排版工具，贴图是贴图发布项目），分发服务按平台写进去。加一个平台，就是分发服务里加一个平台文件、表里加一行账号。

## 边界细则（Codex 复核后定）

1. **接口只传外发通用版正文块。** 排版工具把第三方通用规则全部落进块里：署名声明成一个块、图注合并、图片地址已换成 OSS、去掉裸网址。分发服务只把块写成平台标签，再写进编辑器。（2026-10-24 第 4 步已做，规则全在 `api/distribution_rules.go` 与 `api/distribution_blocks.go`，块的样子见 `docs/distribution-blocks.md`。）
2. **排版工具不实时依赖分发服务。** 平台清单、平台限制从分发服务接口取，账号名单从 FBIF 中台的配置包取（2026-10-25 修订），都缓存在排版工具本地文件。分发服务连不上时，卡片和改稿页照常显示，推送在提交前失败、可以重试；分发服务收稿时再校验一次。没检查过的稿不算检查通过。
3. **账号只在「平台账号」表里。** 排版工具不直接读表（不共享存储）：2026-10-25 起经 FBIF 中台的配置包 `GET /api/config/bundle/layout` 读（中台镜像这张表，按消费者打包，One-Api `docs/hub/`）；之前经分发服务的 `GET /v1/accounts`，已退役。lane 键、幂等键、卡片按钮都用表的 record_id，发稿一律带 account。旧 lane 用一次明确的「云梭 UUID → record_id」对照迁过去，旧 intent、冻结内容、状态、回执原样保留，恢复和补查仍按旧幂等键查；卡片生成、按钮解析、版本校验用同一份账号快照。
4. **通知群照 10-23 裁定放在「平台账号」行上。** 同一「来源公众号 + 载体」的几行必须填同一个群；填得不一样算配置错误，在表里写明，排版工具沿用上一次生效的值。卡片回调鉴权用同一份路由，历史群仍按红线 34 只认静态白名单。
5. **分发记录只由排版工具写**，一篇稿、一个平台账号一行。先落排版工具的 JSON，再经持久 outbox 补到表里；补表失败只重试补表，绝不重跑分发。分发服务的执行结果经 HTTP 回给排版工具。
6. **只有排版工具连飞书长连接。** 同一个飞书应用开两条长连接，事件会随机分给其中一条，还会抢走卡片按钮回调（贴图发布项目 `docs/配置与事件方案.md` 实测）。~~分发服务要用的配置，由排版工具收到事件后经 HTTP 通知它刷新~~（2026-10-25 修订：各服务的配置都从 FBIF 中台的配置包读，每 60 秒带 ETag 问一次，中台不通就用本地快照；只有中台订阅或轮询多维表格，排版工具不再转发配置变化。长连接仍只有排版工具一条，管卡片回调）。
7. ~~**贴图线有自己的资格判断**，排版工具先冻结内容和账号、落 intent，再调分发服务~~（2026-10-27 用户改定：「贴图发抖音归贴图发布项目管，排版工具不做贴图入口，Feed 也不改。」）**贴图线归公众号贴图发布项目**：贴图本来就在那里投稿、审核、进表（后台直接发的也自动进表）、在贴图群出卡片，10-26 已在「已发布」卡上做好「同步到抖音、小红书」（只同步展商介绍，幂等键 `tietu.<记录ID>.<平台>`，同步记录写回它的任务表）。排版工具再从 Feed 绕一圈抓同一条，会一条贴图两张卡、两个按钮，两边幂等键不同、分发服务认不出是同一条。排版工具的机器入口照旧只收文章（红线 33），贴图号照旧过滤掉；哪个公众号发到哪个抖音、小红书号，配在贴图发布项目账号表的「抖音账号」「小红书账号」列（填「平台账号」的 record_id）。细则 5「分发记录只由排版工具写」只管文章。
8. **样稿考卷拆两半。** 排版工具留「FoodTalks 已发布正文 → 外发通用版正文块」，分发服务用同一批块测「正文块 → 平台输出 → 对照编辑手发稿」。平台说明书只留分发服务一份。
9. **每一步都在真编辑器上验，扫码放最后。** 每次切换都用已经登录的号存草稿，验读回、超时、重启恢复和监控契约（红线 30）；抖音只用 `dry_run`。FBIF 各号扫码登录是最后一步。

## 迁移顺序

1. 把本框架写进两个项目的规则（本文件与两边 CLAUDE.md）。
2. （2026-10-24 已完成）账号只留多维表格一份：表加「来源公众号」「通知群」两列，`GET /v1/accounts` 返回它们；排版工具缓存账号快照、发稿带 account、旧 lane 迁到 record_id（服务启动时自动改挂，云梭编号留在 lane 上对回执），自动外发开关随账号挪进表（现在暂停，挪过去也保持关）；代码不再读 `YUNSUO_TARGET_ACCOUNTS_JSON`，`YUNSUO_*` 只剩旧云梭 lane 补查用、不再必填，环境里这几行第 3 步随云梭一起删。这一步接口仍收网页代码。
3. （2026-10-24 已完成）删云梭：客户端，推送、轮询和 45 天补查，链接回填与线上正文核对里只给云梭用的部分，lane 上的云梭字段，卡片里的云梭说法，部署检查，环境里的 `YUNSUO_*`。旧云梭 lane 只显示：已发布的照旧显示，没发出去的可以从卡片重新存草稿（经分发服务），读盘时还在处理中的转待核对。
4. （2026-10-24 已完成）平台格式器搬进分发服务：排版工具只出外发通用版正文块，分发服务按平台文件的 `markup` 写成标签（`service/blocks.mjs`），写草稿接口收 `blocks`、多一个字段就 400；平台限制（标题字数与数法、封面下限、每天上限、文章域名、后台地址）只在分发服务的平台文件，经 `GET /v1/platforms` 给排版工具，缓存在 `distribution-platforms.json`（和账号同一套：校验不过整份不要、留最后一份、5 分钟刷新），从没拿到的平台卡片照常显示、推送在提交前失败；分发服务收稿时再查一遍标题字数与封面下限（422 `cover_too_small`）。考卷拆两半（排版工具 `TestDistributionBlocksGolden`，分发服务 `test/golden.test.mjs`，原来 12 份差别记录逐字节复现）；`yunsuo_*` 改名 `distribution_*`；平台说明书只留分发服务一份。搬之前拿 48 个用例比过旧的 Go 写法与新的「块 → 分发服务写法」，46 个逐字节相同，另 2 个只差视频封面图的 alt。带出的行为变化：视频封面图的 alt 由「视频封面」改为空；头条号草稿链接在 mp.toutiao.com，以前按域名整串比对被丢，现在子域名也认；只隔一个空段的两个列表并成一个；空的整段加粗段不再写出。切换时冻结成旧格式（网页代码）、还没提交过的 lane 提交前失败，提示重新存草稿；已提交过的照旧按原来的幂等键只查。还留在排版工具的：头条号文章链接自动查找（要 A 机的 TikHub 密钥，`publish_external_links.go`，以后搬去分发服务）；摘要字数检查的代码（分发服务不收摘要，上限给 0、不查）。
5. （2026-10-27 已完成）接口说明书由代码生成，跟代码对不上测试就失败：分发服务的 `docs/api.md` 由 `npm run gen:docs` 从路由表（`service/http.mjs`）、错误表（`service/errors.mjs`，每个码一行：HTTP 状态、`outcome`、意思、调用方怎么办）和请求体、记录、正文块、平台限制、登录状态的字段表生成，README 的手写接口部分删掉。请求体校验先过字段表，多一个字段、缺必填都 400。每个错误响应带 `outcome`（`rejected` 没动手、`uncertain` 说不准、`human` 停下等人），排版工具照它认结果，不再按 HTTP 状态猜（带出的变化：读不到「平台账号」的 503 `accounts_unavailable` 以前当说不准、先去查，现在直接记失败、可以重存；程序自己出错一律 500 `internal_error`，不再把 Node 的错误码漏出去）。两边对不上的拦法：分发服务 `test/api-doc.test.mjs`（抛的码都登记、登记的都有地方抛、例子过真校验、真走一遍的记录只带表里的字段），排版工具 `TestDistributionRobotClientMapsResponses` 照共用的接口契约 `api/testdata/distribution-api.json` 把写草稿会回的每个码过一遍。
6. （2026-10-27 改定）贴图线归公众号贴图发布项目，Feed、排版工具都不改。剩下的在贴图发布项目：只填好不发已核对（2026-10-27，`sticker sync-check`：10-26 已发布的展商贴图「致美斋」的登录的号、标题、描述、6 张图的宽高与顺序、可见范围全部对上，抖音自带检测「作品未见异常」，模型没出手，没发布） → 用户点头后在服务器配 `STICKER_DISTRIBUTION_URL` 打开同步（贴图发布服务还没接 FBIF 中台，标题超 20 字的不会自动缩，卡上叫人填「短标题」）→ 抖音真发（含仅自己可见）前问用户。
7. 分发记录和小配置进多维表格，改了靠事件订阅生效。
8. 小红书。
