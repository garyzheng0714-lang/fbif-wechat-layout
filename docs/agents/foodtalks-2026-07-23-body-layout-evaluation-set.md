## 1. 评测目标

本评测集用于检查「自动排版临时文章」与 FoodTalks 正式发布文章的正文结构是否一致，并区分问题发生在：

1. 自动链路的正文抽取或传递；
2. 最新规则渲染；
3. FoodTalks 临时文章/正式文章展示层。

每次回归必须重新请求线上当前激活规则，不能把旧规则快照当成评测依据。

## 4. 取数边界与方法

正文容器统一取 `#article-content`。

- 正文起点：作者/原创声明所在的第一个正文块。
- 正文终点：第一次出现独立段落 `提示：` 之前。
- 排除：标题、摘要、分类、标签、浏览量、固定提示声明及其后的商务合作/二维码/logo 等页脚库。
- 比较维度：
  - 直接子节点类型与顺序；
  - `h2` 章节标题；
  - `strong`、正文链接等行内结构；
  - 正文文本块顺序；
  - 图片数量、顺序、自然尺寸、实际显示尺寸和裂图状态；
  - 图注数量、文本、位置和样式。

本轮还把正式文章正文转换成等价 Markdown，再输入线上最新规则排版页。这个回放只用于定位问题边界，不替代 URL 导入链路验收。

而是该文章被误判成「原创」，压根没走截断分支。同一根因还导致页脚整段丢失，
本节当时未覆盖页脚检查，故「通过」不含页脚。

### 14.3 本轮未验证项

### 14.4 新增待确认项：figure 结构与正式文章不一致

本轮抓取两篇正式文章的正文基线时发现，62628 与 62629 的正文直接子节点

## 15. 2026-07-26 缺陷定位与修复（已上线 `fd5693a`）

§14 留下的尾部残留疑点，追下去查出**两个独立缺陷**。合起来的效果是：从 FBIF
自己公众号导入的文章，**页脚整段丢失，且微信原文导流尾巴不被剪掉**，而侧栏
开关仍显示开启，肉眼不可见。

### 15.1 缺陷一：FBIF 自己的文章被判成「原创」

`site.html` 覆盖了 `resolveIsRepost`，用抓到的 `source_name` 与
`activeRulePack.previewAccountName` 比对，相同即判原创。但 `ft-default` 的
`previewAccountName` 是 `FBIF食品饮料创新`——那是基石 62285 的**预览署名**，
不是站点身份。于是任何来自 FBIF 公众号的文章都会撞上，被当作「自己的原创」：

- 转载页脚不输出；
- `stripWechatTrailer` 只在 `isRepost` 为真时执行，导流尾巴因此保留。

来源是别家公众号时才碰巧正确，这正是该缺陷长期未被发现的原因，也解释了为什么
用户日常使用（多为转载他家稿件）感受不到。

**修法**：删除该覆盖，回落到 `editor-shell` 默认（URL 导入一律转载），与公众号
渠道一致。

### 15.2 缺陷二：网站页脚出厂默认关闭

`defaultFBIFFooterModule` 种子为 `enabled=false`，页脚只能靠前台单篇 override
（localStorage）打开。浏览器攒过状态的人看得到；换电脑、清缓存、新同事第一次
使用即静默丢页脚。红线 #20 要求工具完整输出六段，与该默认值直接矛盾。

**修法**：种子改为默认开启，`ft-default-v1` 升 builtin version 18，让已持久化
规则跟随更新。

### 15.3 验收结果（线上 `fd5693a`，全新浏览器 profile，不触碰任何开关）

| 断言 | 修复前 | 修复后 |
|---|---|---|
| 底部拖尾档位 | 原创 | **转载** ✅ |
| 页脚四段（商务合作 / 加群 / 关注 / 更多资讯） | 全无 | **全部输出** ✅ |
| 微信尾部导流段 | 残留三处 | **已剪干净** ✅ |

预览结尾与正式发布版 62285 一致：`不代表FoodTalks立场` → `FoodTalks商务合作方案`
→ `加入微信群` → `关注公众号` → `点击获取更多全球食品资讯`。

公众号渠道未受影响：`app.html` / `fbif.js` / `mp-blocks` 字节未改（红线 #19）。

### 15.4 仍未闭合

顶部状态维持**不通过**：链路可用且两个缺陷已修，但上述比对尚未完成。
